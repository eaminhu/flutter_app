## 目标与非目标

目标：建立可扩展的客户端框架，优先跑通现货交易：登录、交易对列表、市场详情、K 线、实时行情、盘口、买入/卖出、订单预检、下单、撤单、当前委托、历史订单与现货资产更新。订单类型按实际后端能力提供，首期目标为市价单和限价单。
非目标：首期不覆盖 Web/桌面、Event、Perpetual、CFD，不加入专业技术指标或画线工具，不迁移全部业务。下单与撤单验证仅使用明确允许交易写入的开发/测试环境与测试账户，不使用生产资金。

## 建议架构

lib/app：启动、路由、环境配置、依赖组装与本地化启动。
lib/core/domain：后端无关的市场、订单、持仓、金额模型与业务规则；不依赖 Flutter UI。
lib/core/api：Dart 版 PlatformApi，按现有领域接口分组。
lib/core/adapters：v1、v2、mock 协议映射；后端路径、原始字段、枚举与能力差异仅存在于此层。
lib/core/realtime：订阅生命周期、连接状态、重连与快照恢复。
lib/core/session：会话生命周期、凭证存储接口、退出和用户数据隔离。
lib/core/format：统一金额精度、价格和概率展示规则。
lib/design_system：主题、基础组件、图表 ChartView 与 ChartController。
lib/shell：导航、账户、钱包、共享订单与资产能力。现货资产与杠杆持仓保持不同概念；首期不实现衍生品持仓。
lib/modules/spot：首期现货市场发现与交易体验。后续 Event、Perpetual、CFD 按同样边界扩展；模块之间不互相导入，首期不创建其它模块的占位代码。

模块内采用 View + ViewModel。View 负责显示和交互；ViewModel 管理页面状态和操作；repository 管理共享数据及缓存，通过 PlatformApi 获取数据。纯业务规则留在 core/domain。
建议 Riverpod 统一状态管理和依赖注入，go_router 统一路由，webview_flutter 承载图表。依赖清单、版本及安装命令在环境预检后提出并取得用户确认。

## 数据流与边界

后端 → adapter → PlatformApi → repository → ViewModel → View。
图表数据由 Dart 层通过 ChartController 发送至 WebView。WebView 仅显示图表并回传交互事件，不持有登录凭证、不自行连接后端、不发起交易。
图表资源随 App 打包，不依赖远程 CDN。图表渲染允许展示边界的数值转换，但不得回流为订单、金额或业务计算的权威值；十字线读数遵循统一精度规则。

## 行为状态与错误处理

区分加载、成功、空数据、失败、不支持、断线和数据过期状态。保留旧数据时显示其过期状态，不把断线当作实时数据。
金额、价格和数量以字符串或精确十进制值传递和计算，不使用 double 进行金融计算；缺失值保持缺失。
切换市场或周期时隔离请求和订阅，迟到消息不得更新新图表。
退出、令牌拒绝和切换账号时，同时清理凭证、用户缓存和私有订阅。
重连和返回前台时按后端协议补取快照并恢复订阅，不假定协议具有序号或完整增量恢复能力。
交易请求超时后先核对订单状态，不自动重复提交。

## 会话与接口影响

原生凭证存储通过平台接口封装；实现必须依据 v1/v2 实际会话协议确定，不直接照搬 Web Cookie 方案，也不假设后端已有 refresh token。
框架阶段不要求改变后端契约。先迁移首条链路所需的 PlatformApi 子接口，再逐步补齐，其余接口不使用假成功占位实现。
v1 的 STOMP/SockJS 实时协议必须通过开发环境验证，不能用普通 WebSocket 的可连接性代替兼容性证据。

## 实施顺序与验收

1. 环境预检：定位 Flutter SDK、Android 工具链与可用设备；明确 iOS 构建及真机验证使用的 macOS/Xcode 环境。
2. 基础框架：启动、路由、主题、三语言、环境配置、错误模型与依赖组装。
3. mock 链路：现货交易对列表、详情、盘口、买入/卖出、订单预检、下单与撤单、订单列表和资产展示；覆盖加载、成功、空数据、失败与不支持状态。mock 订单状态必须明确标识为演示数据。
4. 图表验证：在 Android/iOS 真机检查缩放、十字线、历史加载、实时更新、滚动冲突、市场切换及后台恢复。
5. 开发/测试环境链路：登录、现货交易对列表、详情、K 线、实时行情、盘口和订单预检；使用同一市场、相同请求范围与时间口径对照 Web 版原始数据与精度。
6. 交易闭环验收：先确认测试账户及环境允许交易写入，再验证买入/卖出、市价/限价单的实际支持情况、下单、撤单、当前委托、历史订单与可用/冻结余额更新。记录订单 ID、请求、响应、订单状态和资产变化；覆盖拒单、部分成交、撤单失败和请求超时后的状态核对，不自动重复提交。

验证包含分析检查、领域/adapter 测试、页面状态与路由测试、完整构建和真机证据。mock 测试不代表真实后端兼容性已经验证。
